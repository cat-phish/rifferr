# Getting started: a first import with your own beets config

This guide runs Rifferr from a source checkout against a beets setup you already
have. It starts with a **test profile** that works on copies, so nothing in your
real library can change while you learn how the review queue, moves and undo
behave. When that works, the last section switches the profile to your real
library.

Rifferr isn't packaged yet (PyPI and Docker come with F-PACKAGING), so every
command here runs from `backend/` with `uv run`.

## Before you start

- **Rifferr's beets version.** Rifferr runs its own pinned beets (check with
  `uv run beet version`), not the `beet` on your PATH. Newer beets versions
  migrate the library database when they first open it, and they make a backup
  file next to it when they do (`<library>-before-<migration>.bak`). An older
  `beet` may not read the migrated database correctly. **Don't point Rifferr at a
  library DB that an older `beet` still uses** until you've upgraded that `beet`
  to the same version or stopped using it on that library.
- **Plugins load from Rifferr's environment.** Your beets config's `plugins:` list
  is loaded by Rifferr's beets, so a plugin has to be importable there:
  - Plugins bundled with beets are always there, but some need extra Python
    packages. For example, `chroma` needs `pyacoustid` (and the `fpcalc` binary on
    PATH), `lastgenre` needs `pylast`, and `discogs` needs `python3-discogs-client`.
  - Third-party plugins (installed separately from beets) aren't there at all.
  - beets carries on without a plugin it can't import. Rifferr warns about it when
    the worker starts and in the run log of every import.
  - Rifferr's optional extras install the packages for `chroma`, `lastgenre` and
    `discogs`: `rifferr[chroma]`, `rifferr[lastgenre]`, `rifferr[discogs]`, or
    `rifferr[plugins]` for all three. In a checkout, from `backend/`:
    ```bash
    uv sync --extra plugins
    ```
  - Add a third-party plugin's package for a session with `uv run --with`:
    ```bash
    uv run --with beets-copyartifacts3 rifferr serve
    ```
- **Config that runs code needs trust.** A beets config that uses `pluginpath`, the
  `inline` plugin (`item_fields`, `album_fields`) or `hook` runs code. Rifferr won't
  load it until you trust that exact content with `rifferr trust-config <profile>`.
  Any edit to the config needs trusting again.

## 1. Make a beets directory for Rifferr

Rifferr uses a beets config directory (`BEETSDIR`) as is and never writes to it.
Give the test profile its own directory with a copy of your config, so you can
change a few settings without touching the original. You need a copy anyway if
your config is generated by another tool and read-only (Nix home-manager, Ansible,
a dotfiles manager). Copy the file itself, not a symlink to it:

```bash
mkdir -p ~/rifferr-test/{beets,inbox,library}
cp -L ~/.config/beets/config.yaml ~/rifferr-test/beets/config.yaml
```

Then edit `~/rifferr-test/beets/config.yaml`:

```yaml
# A new, empty library for the test, never a copy of your real one: a copied DB
# still lists your real files at their real paths.
directory: ~/rifferr-test/library
library: ~/rifferr-test/beets/library.db

import:
  # Import albums where they are. Rifferr moves them into the library later,
  # after you accept each move in the review queue (the `library.move` step).
  copy: no
  move: no
  log: ~/rifferr-test/beets/import.log
```

Other changes:
- **Make sure `plugins:` includes `musicbrainz`.** In beets 2.x MusicBrainz is a
  plugin. beets loads it by itself only when the config has no `plugins:` list, so a
  config written for an older beets often lists plugins without it. Without a
  metadata source plugin (`musicbrainz`, `discogs`, …) beets can't find candidates
  for any album. If you drop `discogs` because its package is missing, check
  that a source is still left. `beet version`, run from `backend/`, lists the loaded
  plugins:
  ```bash
  BEETSDIR=~/rifferr-test/beets uv run beet version
  ```
- **Remove `copyartifacts` / `copyartifacts3` from `plugins:`.** It doesn't fire
  for Rifferr's moves, and `library.move` has its own `artifacts` rules for logs,
  cue sheets and extra images.
- **Path formats** (`paths:`) in your beets config are only used by beets'
  own moves. The example workflow sets its own path formats on its
  `library.move` step. Compare the two and keep whichever you want.

## 2. Create the profile

```bash
cd backend
uv run rifferr profile create test --beetsdir ~/rifferr-test/beets
```

Profiles live in `~/.config/rifferr/profiles/<name>/` (or `$XDG_CONFIG_HOME/rifferr`,
or `$RIFFERR_CONFIG_DIR`). Open `profiles/test/profile.yaml` and set the folders
the example workflow uses:

```yaml
backend: beets
beets:
  beetsdir: ~/rifferr-test/beets
vars:
  # Absolute paths: `~` is not expanded in vars.
  inbox: /home/you/rifferr-test/inbox        # new albums land here
  library: /home/you/rifferr-test/library    # albums move here after review; same as beets `directory`
secrets: {}
```

If your config uses `inline`, `pluginpath` or `hook`:

```bash
uv run rifferr trust-config test
```

It asks before trusting (`--yes` skips the question).

## 3. Add the example workflow

Copy the example workflow, the workflow it calls and the scripts they use into the
profile:

```bash
P=~/.config/rifferr/profiles/test
mkdir -p $P/workflows $P/scripts
cp ../examples/workflows/{foobar-style,release-suffixes}.yaml $P/workflows/
cp ../examples/scripts/*.yaml $P/scripts/
uv run rifferr validate --profile test --safety $P/workflows/foobar-style.yaml
```

`--safety` prints the static safety report: what the workflow runs, which
files it moves and which secrets it uses. Read it, then trust the workflow (this
trusts `release-suffixes.yaml` too, each by its own hash; without `--profile` the
trust covers every profile):

```bash
uv run rifferr trust --profile test $P/workflows/foobar-style.yaml
```

Files from elsewhere, the repo's `examples/` included, are never trusted
automatically. Editing a trusted file removes its trust, and you trust it again
after reading the change.

The library step's path formats use `%the{}`, which needs the beets `the` plugin.
Add it to your test config's `plugins:` with `the: {a: no, format: "{0}, {1}"}`,
or change those formats.

## 4. Start Rifferr and run an import

Copy two or three albums into the inbox, ideally one that beets matches easily and
one that it won't:

```bash
cp -r "/path/to/music/Some Artist - Some Album" ~/rifferr-test/inbox/
uv run rifferr serve
```

`serve` opens the app in your browser and signs you in. If no browser opens, run
`uv run rifferr sign-in` in another terminal for a one-time link.

Start a run of the whole inbox from the app, or from another terminal:

```bash
uv run rifferr run foobar-style --profile test
```

While `serve` runs, the workflow's watch trigger also starts a run for each new
folder in the inbox once it has been quiet for five minutes.

What to expect:
- Strong matches import without asking. Others wait in the **review queue** as
  import decisions: pick a candidate, search by ID, import as is, or skip. A waiting
  album holds only its own lane, so the rest of the run carries on.
- Release-type suffixes, missing covers and cleanup run next. A cover that no
  provider finds well enough waits for you to choose one.
- Each album's **library move** waits in the review queue, showing the old and new
  folder and every file's old and new name. Accept it and the album moves into
  `library`.
- Every change is journaled. The run page undoes tag changes and moves. Undo of
  an import never deletes the only copy of a file.

## 5. Use your real library

When test runs behave:

1. Upgrade the `beet` you use elsewhere to Rifferr's beets version, or stop using it
   on this library (see *Before you start*). Back up your library DB.
2. Point the profile's beets config at your real `directory` and `library`. Keep
   `import: {copy: no, move: no}` if you want albums to move only after review.
3. Set `vars.inbox` and `vars.library` to your real folders. Trust the beets
   config again (`trust-config`), because it changed.
4. Start with one album.

## When something goes wrong

- **`beets directory … does not exist`, or a "set beets.beetsdir" error:** check
  `beets.beetsdir` in `profile.yaml`. Rifferr never falls back to beets' default
  locations.
- **The worker refuses to load the beets config:** it runs code and isn't trusted,
  or it changed since you trusted it. Run `rifferr trust-config <profile>`.
- **`workflow not trusted`:** the workflow file changed. Re-run `validate` and
  `trust`.
- **`** error loading plugin X`:** the plugin or its Python package isn't in
  Rifferr's environment (see *Before you start*).
- **Every album says "beets found no candidates", or the run log warns that beets has
  no metadata source plugin loaded:** add `musicbrainz` to `plugins:` in the beets
  config (see step 1), trust the config again, and restart `rifferr serve`.
